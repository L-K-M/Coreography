# macOS data sources for CPU, GPU, power and thermals on Apple Silicon (research notes)

> Coreography research notes. Sources accessed 2026-10-17.

Scope: how open-source tools obtain hardware metrics on Apple Silicon (M1-M6 era, incl. M5 "Super" cores) under macOS 26 Tahoe and macOS 27 "Golden Gate", what privileges each path needs, sampling cost, and what broke in macOS 26/27. All file paths cited are real source paths read on GitHub master/main as of 2026-10-17.

## Summary

- Everything interesting comes from four substrates: public Mach/`host_statistics`+`sysctl` calls (free, stable), IOKit IORegistry reads (free, semi-stable), the private `IOReport` dylib (rootless, rich but Apple can and does gate it), and SMC/`IOHIDEventSystemClient` for sensors and rails (rootless reads, privileged writes).
- **macOS 27 broke unprivileged SoC power counters.** The IOReport `Energy Model` channels (`CPU Energy`, `ANE*`, `DRAM*`, `PCI*`) still enumerate but stop incrementing for non-entitled processes; refreshing them appears to require the private entitlement `com.apple.private.pmgr.nrg.reporting`, for which Apple's signed `powermetrics` is the only observed carrier (whether that specific entitlement is the gate, vs platform signing in general, is inferred from codesign inspection in stats #3621, not documented). `sudo` alone does not help. Only the `GPU Energy` (nJ) channel still works. (macmon README "Power sources and macOS 27"; exelban/stats issue #3621; mactop commit c5784ae.)
- Three independent workarounds exist in the wild: (1) macmon reads hidden `AppleCLPC` driver energy reports via opaque `(table_index << 32) | low_id` channel IDs, with per-CLPC-bundle key tables extracted from IPSW kernelcaches; (2) mactop falls back to PMP "Energy" cluster power histograms (verified on M4 Pro/Max and the M5 family; the `Energy` subgroup is absent on M3), `PZD*` (DRAM) and AMC Stats byte counters for ANE; separately, two users in stats issue #3621 summed SMC rails `PP0b`+`PPbb`+`PP7b` as a CPU power estimate (within about 2-10% of other readings on one base M3 and one base M5; Pro/Max/Ultra untested; mactop does not use these keys); (3) while Apple's signed `powermetrics` runs with the `cpu_power` or `gpu_power` sampler, `Energy Model / CPU Energy` advances for other unprivileged readers at powermetrics' cadence (shown for CPU Energy only; not DRAM or ANE; stops when powermetrics exits).
- Per-cluster CPU frequency and residency is rootless via IOReport `CPU Stats` / `CPU Core Performance States` state residencies cross-referenced with `voltage-statesN-sram` DVFS tables in the `pmgr`/`clpc` IORegistry node. Channel names (`ECPU*`, `PCPU*`, `MCPU*`, `DIE_*_`, `EACC_*`, `PACC0_*`) change per chip generation: M5 re-letters the clusters (`P`=Super, `M`=Performance, `E`=Efficiency) and M6 renames channels again (`EACC_*`/`PACC0_*`) and adds a second `pmgr-child` node.
- CPU "topology" is a moving target: `hw.nperflevels`/`hw.perflevel{i}.physicalcpu`/`.name` sysctl, plus IORegistry `cpuN` `cluster-type` (`E`,`M`,`P`) and `cpus` node `e-core-count`/`m-core-count`/`p-core-count`. On M5+ the registry letters remap: `E`→Efficiency, `M`→Performance, `P`→Super, and `p-core-count` actually counts Super cores. Stats and macmon both carry generation-conditional mapping tables.
- GPU utilization, GPU memory and per-process GPU time are all rootless and comparatively stable: `IOAccelerator` `PerformanceStatistics` dict (`Device Utilization %`, `Renderer Utilization %`, `Tiler Utilization %`, `In use system memory`, `Alloc system memory`), and `AGXDeviceUserClient` nodes exposing `IOUserClientCreator` (`pid N, name`) plus `AppUsage[].accumulatedGPUTime` (ns). That last one is exactly Activity Monitor's "%GPU / GPU Time" source.
- Temperatures: SMC `flt`-typed keys `Tp*`/`Te*`/`Ts*` (CPU-ish) and `Tg*` (GPU-ish) work on macOS 14+; the fallback for all generations is `IOHIDEventSystemClient` usage page `0xff00`/usage `0x0005` whose `Product` names look like `pACC MTR Temp`, `eACC MTR Temp`, `SOC MTR Temp`, `GPU MTR Temp`, `PMU tdie N`. Nobody actually knows the official mapping; every project guesses and sanity-filters (0 < t < 150).
- Fans: read rootless via SMC (`FNum`, `F{i}Ac` actual RPM, `F{i}Mn`/`F{i}Mx`, `FS! `/per-fan mode key for control mode). Writing is privileged: Stats ships an `SMJobBless` privileged helper (`eu.exelban.Stats.SMC.Helper`, XPC protocol `setFanMode`/`setFanSpeed`/`resetFanControl`); mactop just requires `sudo` and reports `kIOReturnNotPrivileged` otherwise.
- Per-app FPS: on macOS 27, `metalperftrace listen --pid <pid> --json` streams live per-process Metal frame statistics at 1 s or slower intervals ([macOS 27.0 man page](https://raw.githubusercontent.com/vitorgalvao/macos-man-pages/main/macOS/27/man1/metalperftrace.1)); before macOS 27 there is no per-app source. Other options: display-level swap counters via IOReport `DCP*` groups / `swap` subgroup (Stats uses this for its FPS widget), `CGDisplayStream` frame callbacks (mactop overlay; needs Screen Recording permission), and Apple's own Metal Performance HUD toggleable globally via `defaults write -g MetalForceHudEnabled -bool YES` (user-writable, no root; on 26.2 the MetalHUDHelper app's toggle stopped working while the `defaults` command itself kept working). Per-frame timing of other apps below 1 s resolution would need WindowServer/SIP-protected territory.
- powermetrics remains the reference implementation: 3 IOReport subscriptions (CPU Complex Performance States, CPU Core Performance States, Energy Model), one delta per reporting cycle, `IDLE`/`DOWN`/`OFF` excluded from active residency, real elapsed time in `elapsed_ns`. Requires root and is now also the only entitled Energy Model consumer. macmon's Frida trace documents its internals (`docs/powermetrics-sampling.md`).

## Tools

### powermetrics (Apple, built-in)

- **Status**: `/usr/bin/powermetrics`, ships with macOS, closed source. Requires root. On macOS 27 it is also the only observed carrier of the private entitlement `com.apple.private.pmgr.nrg.reporting`, which appears to gate `Energy Model` counter updates (the exact gating check is inferred, not documented). macmon's README documents this; a Frida trace of powermetrics is documented in `vladkens/macmon/docs/powermetrics-sampling.md`.
- **What it shows**: per-cluster and per-core active/down/idle residencies and active frequencies, package/CPU/GPU/ANE/DRAM/PCI/ISP/AVE/display energy, GPU residency, thermal pressure, per-task energy/GPU time (samplers `cpu_power`, `gpu_power`, `thermal`, `tasks`, `ane_power`, etc.).
- **How it shows it**: plists/text stream (`-f plist`, `-o <file>`), consumed by asitop and older tools.
- **Internals (from the Frida trace)**: creates three IOReport subscriptions - `CPU Stats`/`CPU Complex Performance States` (4 channels), `CPU Stats`/`CPU Core Performance States` (one per core), `Energy Model` (136 channels on M2). Takes one `IOReportCreateSamples` per subscription per cycle, computes `IOReportCreateSamplesDelta` vs previous; interval controls only the cadence, no hidden subdivision; `elapsed_ns` records the true window (≈+9ms at 1000ms). CPU states `[IDLE, ...]` and `[DOWN, IDLE, ...]` are both excluded from "active"; a core in `DOWN` is not gone (M5 Max P-cluster can sit 99.8% DOWN while a sibling cluster works). Side effect: while powermetrics runs, its samplers re-enable Energy Model counter updates for every other unprivileged process (observed in the stats issue #3621 thread: the `cpu_power` and `gpu_power` samplers trigger it, `tasks`/`ane_power` do not - an empirical workaround, not a guarantee).
- **Ideas worth taking**: one IOReport delta per wall-clock interval, real elapsed time for energy→power conversion, never infer topology from transient DOWN/OFF states.
- **Weaknesses / avoid**: requires root; on macOS 27 beta it was itself broken (CPU Power 0mW under load, per mactop commit c5784ae); plist output is heavyweight to parse.
- **Sources**: https://github.com/vladkens/macmon/blob/main/docs/powermetrics-sampling.md, https://github.com/vladkens/macmon/blob/main/readme.md, https://github.com/metaspartan/mactop/commit/c5784aef8d4a261098bfc62dab0e9e4820b860b5

### IOReport (private API used by every sudoless tool)

- **Status**: private framework/dylib `/usr/lib/libIOReport.dylib` (mactop links `-lIOReport`, macmon binds `#[link(name="IOReport", kind="dylib")]`, Stats declares the functions in `Modules/*/bridge.h`). No headers or docs; all signatures are reverse-engineered (canonical reference: `freedomtan/sensors` for IOHID, `tlkh/asitop` and `dehydratedpotato/socpowerbud` lineage for channels). App-store-safety of the private API is unverified, though Stats ships on the Mac App Store (unverified whether current builds are accepted).
- **What it shows**: kernel-published counters organized as group → subgroup → channel with units: `Energy Model` (energy in mJ/uJ/nJ/pJ: `CPU Energy`, `DIE_N_CPU Energy` on Ultra, `GPU Energy`, `ANE*`, `DRAM*`, `GPU SRAM*`, `PCI* Energy`, `ISP`, `AVE`), `CPU Stats`/`CPU Complex Performance States` + `CPU Core Performance States` (state residencies: `IDLE`/`DOWN`/`OFF` + frequency states), `GPU Stats`/`GPU Performance States` (`GPUPH` channel), `AMC Stats` (DRAM `DCS`/`DCS RD`/`DCS WR`/`DCS_*` byte counters, `ANE* RD/WR` fabric counters), `PMP`/`PMP0`/`PMP1` (AMCC rate histograms, ANE floors, `Energy`/`PACC`/`MACC1`/`PACC0 SRAM` cluster power histograms, `DRAM BW`), `CLPC`/`Energy Counters` (hidden synthesized channels), `DCP*`/`swap` (display swaps), `ODS`, `Performance Statistics` (group enumeration seen in mactop's dump list).
- **Call model**: `IOReportCopyAllChannels` or `IOReportCopyChannelsInGroup(group, subgroup, 0,0,0)` → merge via `IOReportMergeChannels` → `IOReportCreateSubscription(nil, channels, &subscribed, 0, nil)` → sample twice + `IOReportCreateSamplesDelta`. Read via `IOReportChannelGetGroup/SubGroup/ChannelName/UnitLabel/DriverID/ChannelID`, `IOReportSimpleGetIntegerValue`, `IOReportStateGetCount/NameForIndex/Residency`.
- **Privileges**: enumerating and sampling is rootless on macOS ≤26. On macOS 27, `Energy Model` non-GPU channels freeze without the pmgr entitlement; on M5 Max/Ultra the bare `PMP` group is empty because the channels moved to per-die `PMP0`/`PMP1` (base M5 still exposes them under `PMP`); `CLPC` synthetic channels still work (macmon's workaround).
- **Sample cost**: `IOReportCreateSamples` on a large merged set costs tens of ms (mactop anchors `mach_absolute_time` after each call; notes ~10-20% BW under-reporting if mis-anchored). PMP adds "hundreds of channels" and measurably raises per-call kernel IPC cost - mactop merges only name-filtered PMP channels. Stats' frequency reader takes 4 deltas of ~125ms each (~500ms total) per read.
- **Pitfalls**: cumulative counters can reset or return negative deltas (macmon discards); units differ per channel (`unitLabel` must be read, default nJ); state names are provider-defined (`IDLE`/`DOWN`/`OFF` excluded from active); channel names change per chip (`DIE_0_PCPU1_CPU0` on Ultra).
- **Sources**: https://github.com/vladkens/macmon/blob/main/src/sources.rs, https://github.com/vladkens/macmon/blob/main/src/shared.rs, https://github.com/metaspartan/mactop/blob/main/internal/app/ioreport.m, https://github.com/exelban/stats/blob/master/Modules/GPU/bridge.h

### macmon (vladkens) - Rust, sudoless

- **Status**: active; v0.10.0 released 2026-10-14 on GitHub (the changelog says 2026-10-15), three days before research date. MIT. CLI/TUI + Rust library (`cargo add macmon --no-default-features`), `pipe` JSON and `serve` Prometheus/HTTP modes, brew formula.
- **What it shows**: CPU/GPU/ANE/DRAM/GPU-SRAM/system power, per-tier (E/P/S) and per-core frequency + active/scaled residency, avg CPU/GPU temp, fan RPM+max, RAM/swap, per-process CPU/mem/power/GPU, SoC info (chip, tiers, freq tables, `vm` flag).
- **How it shows it**: ratatui TUI with boxed metric panels (power row, CPU tiers, temps, fans, memory) above an htop-style process list; sparkline history with avg/max; JSON `macmon pipe`, Prometheus exporter, Grafana example.
- **Data sources (paths)**: `src/sources.rs` - raw FFI bindings to IOReport + IOKit + IOHID + SMC (`AppleSMC`/`AppleSMCKeysEndpoint`, classic `SMCKeyData` struct method 2); `src/clpc.rs` - macOS 27 CLPC workaround tables per driver bundle (`com.apple.driver.AppleT6000CLPCv3` … `AppleT8152CLPC` = T6xxx + T8xxx families); `src/metrics.rs` - power-source priority `clpc.or(energy_model).unwrap_or(pmp)` per component; `src/shared.rs` - the exact channel filter (`Energy Model`: `GPU Energy`, `*CPU Energy`, `ANE*`, `DRAM*`, `GPU SRAM*`; `CPU Stats`/`CPU Core Performance States`; `GPU Stats`/`GPU Performance States`; PMP `Energy Counters` `ANE*` in mJ/uJ/nJ). Topology: `hw.nperflevels`/`hw.perflevel{i}.physicalcpu`/`.name` + `cpuN` `cluster-type` + `pmgr` `acc-clusters`/`voltage-states{1,5,9,...}-sram`. Temps: SMC `Tp*`/`Te*`/`Ts*`/`Tg*` float keys first (exist since macOS 14), IOHID `0xff00`/`0x0005` fallback. Fans: all `F?Ac` keys + `F?Mx` max. System power: SMC `PSTR`. Memory: libc/`host_vm` counters. CPU usage fallback: `host_processor_info` ticks when IOReport CPU Stats absent (VM).
- **M5/M6 channel naming (from code comments, issues #47/#80)**: M1-M4 `ECPU*`/`PCPU*`; M5 base `PCPU*`=Super + `ECPU*`=Efficiency; M5 Pro/Max `PCPU*`=Super + `MCPU*`=Performance (M is a distinct middle tier, not renamed E); M6 exposes all three: `EACC_ECPU*`, `PACC0_MCPU*`, `PACC0_PCPU*`; Ultras prefix `DIE_N_` (e.g. `DIE_0_PCPU1_CPU0`).
- **Ideas worth taking**: `PowerSources` triple-fallback design (clpc/energy-model/pmp with validity rules); honest degradation (`Option<f32>` temps, `null` in VM); per-core → tier → combined aggregation with documented math (`active_ratio`, `scaled_ratio`); `get_sample_interval` keeps a baseline so intervals never overlap; SMC key enumeration at init instead of hardcoded lists; `find-clpc` diagnostic subcommand pattern.
- **Weaknesses / avoid**: CLPC tables are per-OS-version and per-driver - `INDICES_27` (cpu=16, gpu=25, ane=24) changed vs 26 (gpu 24→25, ane 23→24) and will need re-extraction per release (`docs/clpc-discovery.md`, scripts download IPSW kernelcaches and trace Mach-O); unknown driver = silently zero power unless guarded.
- **Sources**: https://github.com/vladkens/macmon/blob/main/readme.md, https://github.com/vladkens/macmon/blob/main/src/sources.rs, https://github.com/vladkens/macmon/blob/main/src/metrics.rs, https://github.com/vladkens/macmon/blob/main/src/clpc.rs, https://github.com/vladkens/macmon/blob/main/src/shared.rs, https://github.com/vladkens/macmon/blob/main/docs/clpc-discovery.md, https://github.com/vladkens/macmon/blob/main/docs/powermetrics-sampling.md, https://github.com/vladkens/macmon/blob/main/changelog.md

### mactop - Go + cgo/ObjC (context-labs → metaspartan v2)

- **Status**: original `context-labs/mactop` README redirects to `metaspartan/mactop` ("mactop v2"), which is very actively developed (M5/S-core support, macOS 27 fixes, 20 locales). MIT. brew formula `mactop`. Monitoring is rootless; fan control writes SMC and requires `sudo` (returns `kIOReturnNotPrivileged` otherwise).
- **What it shows**: CPU/GPU/ANE/DRAM/system power, GPU freq + active %, E/P/S-core per-core usage via Mach API, temps (SMC with human-readable labels + IOHID fallback), thermal state, fan RPM/target/mode, DRAM read/write bandwidth (GB/s), ANE bandwidth + power-state fallback, memory pressure (`kern.memorystatus_vm_pressure_level`), battery %, per-process GPU (experimental), network/disk/thunderbolt, display FPS overlay.
- **Data sources (paths)**: `internal/app/ioreport.m` (one very large ObjC file) - same IOReport group set as macmon plus `AMC Stats` (M1-M4 DRAM DCS byte counters), filtered `PMP`/`PMP0`/`PMP1` (M4 Pro/Max AMCC DCS-BW rate histograms, ANE `AF BW`/`DCS-BW` floors, CPU `Energy`/`PACC`/`MACC1`/`PACC0 SRAM` cluster power histograms used when Energy Model reads 0), `CLPC`, `ODS`, `Performance Statistics`; `internal/app/smc.c` SMC incl. fan control and rail keys `PSTR`/`PDTR`/`PD0R` (system power fallbacks for laptops/desktops), `PZD1`/`PZD2` (DRAM power on macOS 27, verified on M5 Max); `internal/app/native_stats.go` - `host_statistics64`, `getifaddrs`/SIOCGIFMEDIA link speeds, `AppleAPFSVolume` Statistics, and **per-process GPU**: child iterator under `AGXAccelerator` for `AGXDeviceUserClient` nodes, PID parsed from `IOUserClientCreator` (`"pid N, name"`), GPU time summed from `AppUsage[].accumulatedGPUTime` (ns); `internal/app/displayfps.m` - FPS via `CGDisplayStream` on the main display (needs Screen Recording permission; counted with `CGDisplayStreamUpdateGetDropCount`); kperf/kpep dlopen fallback for DRAM BW estimation (root path).
- **macOS 27 handling**: detects frozen Energy Model counters (`g_energyModelCpuGated`/`g_energyModelDramGated`), renames handled (bare `ANE`, `GPU`, `DRAM`, block channels `ANE0_0`, `DRAM0_0`), ANE fallback chain: PMP floors → AMC `ANE* RD/WR` bytes (~2.2 GB/s under forced CoreML load) → `H11ANEIn` `IOPowerManagement.CurrentPowerState` duty-cycle sampling at ~50ms cadence, with `IOExclaveProxy`/`IONameMatched "ane,*exclave"` detection on M5 (exclave ANE power state is pinned high by background ML services, so shown as binary on/idle, not %).
- **Ideas worth taking**: graceful per-metric fallback ladders with hysteresis (latch fallback once proven dead); DRAM BW auto-calibration (power-based GB/s-per-watt estimate when no byte counters); temperature floor `kSiliconMinTempC = 10.0` filters bogus post-boot readings; cached IOHID client (create costs ~2-5ms IPC); SMC power rail research comments (PSTR laptop total, PDTR/PD0R desktop rails).
- **Weaknesses / avoid**: a huge hand-rolled ObjC file is a cautionary tale in complexity; kperf path needs root; GPU per-process is "experimental" and proportional-only.
- **Sources**: https://github.com/metaspartan/mactop/blob/main/README.md, https://github.com/metaspartan/mactop/blob/main/internal/app/ioreport.m, https://github.com/metaspartan/mactop/blob/main/internal/app/native_stats.go, https://github.com/metaspartan/mactop/blob/main/internal/app/displayfps.m, https://github.com/context-labs/mactop/blob/main/internal/app/ioreport.m, https://github.com/metaspartan/mactop/commit/c5784aef8d4a261098bfc62dab0e9e4820b860b5

### asitop (tlkh) - Python, needs sudo

- **Status**: unmaintained (last push 2024-04-18, ~4.6k stars). MIT. pip package. Was the tool that popularized `powermetrics` parsing.
- **What it shows**: E-CPU/P-CPU/GPU usage gauges + per-core vertical gauges, ANE gauge (power÷8W as proxy), RAM/swap, CPU/GPU power charts with peak + rolling average.
- **How it works**: spawns `sudo powermetrics --samplers cpu_power,gpu_power,thermal -f plist -i <ms>` writing plist output to a per-process temp file (`asitop/utils.py`), parses it with `plistlib` (`asitop/parsers.py`) for `E-Cluster_active`, `E-Cluster_freq_Mhz`, per-core actives, `ane_W`, `thermal_pressure`; `sysctl hw.perflevel{0,1}.logicalcpu` for core counts; `system_profiler SPDisplaysDataType` for GPU cores; `psutil` for RAM; hardcoded TDP/bandwidth tables per chip.
- **Ideas worth taking**: nvtop-style gauge layout is exactly the "graphs first, process list second" model Coreography wants - but implemented natively.
- **Weaknesses / avoid**: root requirement; shelling to powermetrics per interval; assumes exactly 2 perflevels (breaks on M5/M6 3-tier and VM); hardcoded TDPs.
- **Sources**: https://github.com/tlkh/asitop/blob/main/asitop/asitop.py, https://github.com/tlkh/asitop/blob/main/asitop/utils.py, https://github.com/tlkh/asitop/blob/main/README.md, https://api.github.com/repos/tlkh/asitop

### Stats (exelban) - Swift menu-bar app

- **Status**: active; 3.0.x series (3.0.16 Sep 2026, 3.0.21 Oct 2026 per issue comments). Free on GitHub (MIT license, verified via repo metadata); paid App Store build (unverified). Runs entirely unprivileged except an optional `SMJobBless` helper for fan control.
- **What it shows**: per-module readers for CPU (per-core usage, E/P/S cluster usage, freq, temp, thermal limit), GPU (utilization, renderer/tiler, temp, clock, ANE util, FPS), Sensors (all SMC temps/voltages/currents/powers + HID sensors + IOReport power), Battery, plus modules not covered here.
- **Data sources (paths)**:
  - `Modules/CPU/readers.swift`: `host_processor_info(machHostPort, PROCESSOR_CPU_LOAD_INFO, ...)` per-core tick deltas (user/system/nice/idle); `host_statistics(HOST_CPU_LOAD_INFO)` for system/user/idle aggregate; `sysctl hw.physicalcpu`/`hw.logicalcpu` (hyperthreading), `hw.ncpu`; per-cluster usage by grouping `usagePerCore` via SystemKit `core_s.type` (`.efficiency`/`.performance`/`.super`); `ProcessReader` literally shells `/bin/ps -Aceo pid,pcpu,comm -r` for top processes; `TemperatureReader`; `FrequencyReader` (inspired by shank03/StatsBar IOReport.swift): subscribes `CPU Stats`/`CPU Complex Performance States`+`CPU Core Performance States`, takes 4×125ms deltas per ~500ms read, matches channels `ECPU`/`PCPU`/`MCPU` (perf tier = `PCPU` when no S cores, `MCPU` when S cores exist - the M5 quirk), computes residency-weighted frequency against `eCoreFrequencies`/`pCoreFrequencies`/`sCoreFrequencies` DVFS tables with min-freq floor; `LimitReader` shells `pmset -g therm` for CPU speed limit.
  - `Modules/GPU/reader.swift`: `fetchIOService(kIOAcceleratorClassName)` → `PerformanceStatistics` dict: `Device Utilization %` (fallback `GPU Activity(%)`), `Renderer Utilization %`, `Tiler Utilization %`, `Temperature(C)`, `Fan Speed(%)`, `Core Clock(MHz)`, `Memory Clock(MHz)`; `AGCInfo.poweredOffByAGC` power state; AMD/Intel temp fallback to SMC `TGDD`/`TCGC`; `maxANEPower` table per platform (M1 through M6 generations) for ANE utilization = ANE watts / max; ANE power from `Energy Model` `ANE*` cumulative energy ÷ wall clock; **FPS from IOReport `DCP`,`DCP0`,`DCPEXT0-3` groups, subgroup `swap`** - delta of swap counter ÷ elapsed = system-wide display FPS.
  - `Modules/Sensors/readers.swift` + `values.swift`: SMC key enumeration, type guessed by first letter (`T`/`V`/`P`/`I`), names mapped via a curated list (Intel-oriented; unknown keys shown with group `.unknown` when setting enabled); M2 workaround: CPU-group temps <10 or >120 rejected; HID sensors (`0xff00`/`5` temp, `0xff08`/`2` current, `0xff08`/`3` voltage) behind `Sensors_hid` setting, ObjC `reader.m` keeps a cached `IOHIDEventSystemClient` with 60s service rediscovery (5s when events missing); IOReport `Energy Model` → computed sensors `CPU Power`/`GPU Power`/`ANE Power`/`RAM Power`/`PCI Power` (cumulative energy deltas ÷ elapsed); `PSTR`-derived cumulative "Total System Consumption" Wh and "Average System Total" W; fans via `FNum` count + `F{i}Mn`/`F{i}Mx`/`F{i}Ac` + mode (`FS! ` bitmask on Intel-era, `F{i}Md`-style key on ARM); `initCalculatedSensors` adds `Average/Hottest CPU`, `Average/Hottest GPU`, `Average/Hottest SOC`, `Fastest fan`.
  - `Modules/Sensors/reader.m`: `StatsHIDSensorSource` - `IOHIDEventSystemClientCreate` + `SetMatching` + `CopyServices` + per-service `Product` name + `IOHIDServiceClientCopyEvent(type,0,0)` + `IOHIDEventGetFloatValue(IOHIDEventFieldBase(type))`.
  - `SMC/smc.swift`: full SMC client (`IOServiceMatching("AppleSMC")`, `IOServiceOpen`, `IOConnectCallStructMethod` index `kernelIndex=2`, commands `readBytes=5`, `readKeyInfo=9`, `readIndex=8` for `getAllKeys`); decodes all spXX/fpe2/flt/ui8/16/32 types; `SMC/Helper/` = `eu.exelban.Stats.SMC.Helper` privileged launchd job (installed via SMJobBless, helper plist in repo) exposing XPC `HelperProtocol` (`setFanMode`, `setFanSpeed`, `resetFanControl`) - this is the sanctioned way to get fan control without running the app as root.
  - `Modules/Battery/readers.swift`: `IOPSNotificationCreateRunLoopSource` event-driven updates, `IOPSCopyPowerSourcesInfo`+`IOPSGetPowerSourceDescription` (type `InternalBattery`, also handles UPS); `AppleSmartBattery` registry props `Amperage`(mA), `Voltage`(mV), `CycleCount`, `AppleRawCurrentCapacity`, `AppleRawMaxCapacity`/`NominalChargeCapacity`/`DesignCapacity`, `BatteryData`, `ChargerData` (`ChargingCurrent`/`ChargingVoltage`/`NotChargingReason`); charge/discharge watts = `Voltage` × `Amperage`; adapter power from `ChargerData`/`IOPSCopyExternalPowerAdapterDetails`; temp fallbacks `Temperature` prop → `AppleSmartBatteryPack`→`TB1T`/`TB2T`.
  - `Kit/plugins/SystemKit.swift`: platform enum m1…m6(+a18Pro); core typing via `cpuN` `cluster-type` bytes - on M5+ `E`→efficiency, `M`→performance, `P`→super (older: `E`/`P` only); `cpus` node `e-core-count`/`m-core-count`/`p-core-count` on M5+ (p-core counts Super); frequencies: `pmgr` (M6 also `pmgr-child`) `voltage-states1-sram`(E), `voltage-states5-sram`(P ≤M4, S on M5+), `voltage-states22-sram`(M on M5+), `convertCFDataToArr` handles Hz scaling that changed at M4; model/platform from `hw.model`/`IOPlatformExpertDevice`/`machdep.cpu.brand_string`; GPU info shells `system_profiler SPDisplaysDataType -json`.
- **macOS 26/27 breakage observed**: menu-bar widgets invisible on Tahoe 26.6.1 (#3535), `setNeedsDisplayInRect` → SkyLight `Invalid window` spam; open PR #3216 proposes layer-backed rendering (not merged as of 2026-10-17), detail-window flicker on 27 (#3619), and #3621 `CPU Power 0.00W` on macOS 27 (Energy Model freeze; community found SMC rail + PMP histogram workarounds - `PP0b` P-cluster, `PPbb` E-cluster, `PP7b` CPU SRAM on M3 and M5, `PP1b` GPU, `PZC0`/`PHPC`/`PHPS` whole-SoC; issue left open by maintainer).
- **Ideas worth taking**: the reader/subscription architecture (each metric a `Reader<T>` with interval + callback); cumulative-energy÷elapsed power derivation; fan enumeration not hardcoding; privileged-helper boundary (monitor rootless, control via SMJobBless); `Platform` enum + per-generation mapping centralized in one SystemKit file.
- **Weaknesses / avoid**: shells `ps` and `pmset` per refresh; Intel-era SMC names mislabel Apple Silicon keys (mactop's human-readable labels are better); no mitigation yet for the macOS 27 power freeze.
- **Sources**: https://github.com/exelban/stats/blob/master/Modules/CPU/readers.swift, https://github.com/exelban/stats/blob/master/Modules/GPU/reader.swift, https://github.com/exelban/stats/blob/master/Modules/Sensors/readers.swift, https://github.com/exelban/stats/blob/master/Modules/Sensors/reader.m, https://github.com/exelban/stats/blob/master/Modules/Sensors/values.swift, https://github.com/exelban/stats/blob/master/SMC/smc.swift, https://github.com/exelban/stats/blob/master/SMC/Helper/protocol.swift, https://github.com/exelban/stats/blob/master/Modules/Battery/readers.swift, https://github.com/exelban/stats/blob/master/Kit/plugins/SystemKit.swift, https://github.com/exelban/stats/issues/3621

### btop (aristocratos) - C++ TUI

- **Status**: active; latest release v1.4.7 (2026-05-01), Apache-2.0. `src/osx/` backend is still the thinnest Apple Silicon coverage of the tools surveyed, but it does have one IOReport path for GPU metrics.
- **What it shows** (macOS side): CPU usage/per-core via Mach calls, memory, disks, network; per-core temps on Intel, and on Apple Silicon IOHID-sourced ACC/die/SoC temps plus GPU utilization, power and frequency.
- **Data sources (paths)**: `src/osx/btop_collect.cpp` - `host_processor_info(PROCESSOR_CPU_LOAD_INFO)` per-core tick deltas (summed for the total), `host_statistics64(HOST_VM_INFO64)` for memory, `getloadavg` for load; an AppleSilicon-specific block subscribes IOReport `GPU Stats`/`GPU Performance States` (`GPUPH` channel → utilization) and `Energy Model` `GPU Energy` (→ watts), with the `pmgr` `voltage-states9` DVFS table for GPU frequency; `src/osx/smc.cpp` - classic SMC `TC*` per-core keys (Intel-era; return -1 on AS); `src/osx/sensors.cpp` - `IOHIDEventSystemClient` `0xff00`/`5` temps, bucketed by `Product` name: `eACC`/`pACC` → ACC temps, `PMU tdie N` → per-"core" temps, `SOC MTR Temp Sensor` → SoC; comments admit the mapping is guesswork ("nobody knows which sensors mean what", notes `PMU tdie 3 and 9` missing, `PMU tdev` negative).
- **Ideas worth taking**: nothing unique data-wise; its value is UX (not this document's scope).
- **Weaknesses / avoid**: no CPU frequency/power or ANE metrics on AS - its single IOReport use covers only the GPU.
- **Sources**: https://github.com/aristocratos/btop/blob/main/src/osx/smc.cpp, https://github.com/aristocratos/btop/blob/main/src/osx/sensors.cpp, https://github.com/aristocratos/btop/blob/main/src/osx/btop_collect.cpp

### socpowerbud (dehydratedpotato) - ObjC, sudoless

- **Status**: sporadically maintained; reverse-engineered `powermetrics`; influenced NeoAsitop. Binary `socpwrbud` + `iorepdump` diagnostic tool.
- **What it shows**: per-cluster AND per-core DVFS: average frequency, average voltage, active/idle residency, and per-state DVFS distribution histograms (`744 MHz (790 mv): 31.84%`), for CPU clusters and the integrated GPU. Power metrics are currently missing per its README ("missing for now").
- **How it works**: same IOReport subscription pattern (`CPU Stats`/`GPU Stats` residencies + pmgr voltage-states tables), but also resolves per-state voltage from the DVFS tables - something the other tools don't surface.
- **Ideas worth taking**: DVFS distribution view (freq×voltage×residency histogram) is a unique visualization worth stealing for a "what clock is the cluster actually at" panel; `iorepdump` approach of shipping a channel-dump diagnostic.
- **Weaknesses / avoid**: Max/Ultra multi-cluster topologies buggy per README; power removed.
- **Sources**: https://github.com/dehydratedpotato/socpowerbud/blob/main/README.md

### NeoAsitop (op06072) - Swift, sudoless

- **Status**: Swift rewrite combining socpowerbud's IOReport approach with Stats' sensor code (`SensorUtil/readers.swift`, `smc.swift` are visibly Stats-derived). Unmaintained (last push 2024-07-16); functionally sudoless.
- **What it shows**: asitop-style UI plus full sensor list (SMC enumeration, HID temps, PSTR-derived cumulative Wh - same code shape as Stats).
- **Ideas worth taking**: demonstrates the whole stack is implementable in pure Swift (+ bridging header for IOReport/IOHID), i.e. directly applicable to Coreography.
- **Weaknesses / avoid**: forks Stats code, including its Intel-centric key naming.
- **Sources**: https://github.com/op06072/NeoAsitop, https://github.com/op06072/NeoAsitop/blob/main/SensorUtil/readers.swift

### SMC + IOHIDEventSystemClient (sensor substrate)

- **Status**: SMC = the classic `AppleSMC` IOKit service (`IOServiceOpen` + `IOConnectCallStructMethod` selector 2, `SMCKeyData` command structs: `readBytes=5`, `readKeyInfo=9`, `readIndex=8`, `readPLimit=11`, `writeBytes=6`). Reads are rootless; writes privileged. Present on all Apple Silicon Macs (absent in VMs). IOHIDEventSystemClient = private IOHIDFamily API to `hidd`; rootless reads.
- **What it shows**: SMC - thousands of 4-char keys: temps (`T*`), voltages (`V*`), currents (`I*`), power rails (`P*`), fans (`F*`), plus system totals (`PSTR`/`PDTR`/`PD0R`), DRAM (`PZD*`), CPU rails reported by single users on base M3/M5 in stats issue #3621 (`PP0b` P-cluster, `PPbb` E-cluster, `PP7b` CPU SRAM, `PP1b` GPU). IOHID - `Product`-named sensors: `pACC MTR Temp`/`eACC MTR Temp`/`SOC MTR Temp`/`GPU MTR Temp`/`PMU tdie N`/`PMU tdev` (temp `0xff00`/`0x0005` event type 15; current `0xff08`/`0x0002`; voltage `0xff08`/`0x0003` per Stats' `m1Preset`, mirrored by NeoAsitop).
- **Cost/pitfalls**: ~µs per SMC key read but enumerate once at init; key availability/meaning varies per model and is undocumented (VirtualSMC's `SMCSensorKeys.txt` is the de-facto dictionary); bogus readings exist (reject ≤0 or >110-150°C, mactop's `kSiliconMinTempC=10`; Stats' M2 <10/>120 CPU fix; `PMU tdev` negative); IOHID client creation costs ~2-5ms - cache it; SMC writes for fan control are `kIOReturnNotPrivileged` without root/helper.
- **Ideas worth taking**: treat sensor name→meaning as per-platform data tables, filter/validate every reading, average ACC sensors for CPU temp.
- **Weaknesses / avoid**: no official documentation; guessing will mislabel sensors on new chips.
- **Sources**: https://github.com/vladkens/macmon/blob/main/src/sources.rs, https://github.com/exelban/stats/blob/master/Modules/Sensors/values.swift, https://github.com/exelban/stats/blob/master/Modules/Sensors/reader.m, https://github.com/metaspartan/mactop/blob/main/internal/app/ioreport.m, https://github.com/aristocratos/btop/blob/main/src/osx/sensors.cpp

### Thermal state, fans and battery

- **Thermal pressure**: `NSProcessInfo.thermalState` (0 Nominal/1 Fair/2 Serious/3 Critical) + `NSProcessInfoThermalStateDidChangeNotification`; asitop instead parses it out of powermetrics output. mactop's `getThermalState` prefers the rawer source: it reads the `com.apple.system.thermalpressurelevel` kernel notification via `notify_get_state` (the `OSThermalPressureLevel` scale `powermetrics --samplers thermal` reports) and falls back to `NSProcessInfo.thermalState`, which can lag because it caches. CPU speed limit from `pmset -g therm` (Stats `LimitReader`). Rootless.
- **Fans**: `FNum` fan count; `F{i}Ac` actual RPM; `F{i}Mn`/`F{i}Mx` range; mode via `FS! ` bitmask (Intel-era) or a per-fan mode/target key on ARM. macmon: any `F?Ac` key → `fanN`, max from `F?Mx`. Control = SMC write → privileged (Stats `SMJobBless` helper `eu.exelban.Stats.SMC.Helper`, `SMC/Helper/protocol.swift`; mactop requires sudo for fan control). Non-root reads are safe on all fan-equipped Macs; desktops report 0 RPM gracefully; some M2-era machines misreport 0 RPM (mactop comments).
- **Battery**: `IOPSCopyPowerSourcesInfo`/`IOPSGetPowerSourceDescription` + `IOPSNotificationCreateRunLoopSource` (public IOKit.ps), `AppleSmartBattery` IORegistry (`Amperage`, `Voltage`, `CycleCount`, `BatteryData`, `ChargerData`), `IOPSCopyExternalPowerAdapterDetails` (adapter W/V). Charge/discharge watts: computed V×I from `Voltage`/`Amperage` (the SMC `PPBR` rail is an alternative battery-power reading). `PDTR`/`PD0R` are DC-in rails mactop uses for desktop system power, not a battery value. All rootless.
- **Sources**: https://github.com/exelban/stats/blob/master/Modules/Battery/readers.swift, https://github.com/exelban/stats/blob/master/SMC/Helper/protocol.swift, https://github.com/metaspartan/mactop/blob/main/README.md, https://github.com/vladkens/macmon/blob/main/src/metrics.rs

### FPS and per-process GPU measurement

- **System FPS**: Stats counts `DCP`/`DCP0`/`DCPEXT0..3` `swap` channels (rootless, display-engine swaps ≈ presented frames). mactop counts `CGDisplayStream` completions on the main display (needs Screen Recording TCC permission; `CGPreflightScreenCaptureAccess` to check). Neither measures a specific app.
- **Per-app FPS**: on macOS 27, `/usr/bin/metalperftrace listen --json --pid <pid> --interval 1` streams live per-process Metal statistics (documented in the macOS 27.0 man page; used by zzoko/PerformanceHUD); `metalperftrace setup --enable hud --pid <pid>` turns on the Metal HUD in a running process. No public API before macOS 27. Options that don't exist: WindowServer frame callbacks are private/SIP-gated; `CVDisplayLink`/`CADisplayLink` measure only your own process's display callbacks (ProMotion cadence, not app FPS); injecting `MTL_HUD_ENABLED` into foreign apps requires code injection (SIP blocks). Apple's Metal Performance HUD is the only sanctioned per-app overlay: `MTL_HUD_ENABLED=1` env, `MetalHUDEnabled` Info.plist key, or global `defaults write -g MetalForceHudEnabled -bool YES` (user domain, no root; MetalHUDHelper toggles it via CFPreferences + a Tahoe Control Center control; on Tahoe 26.2 the MetalHUDHelper app's toggle stopped working while the reporter could still use the `defaults` command, and the app's toggle worked again on the 26.3 RC per MetalHUDHelper issue #4; HUD shows FPS, frame intervals, GPU time per frame, direct-vs-composited presentation).
- **Per-process GPU time** (Activity Monitor's GPU/%GPU columns): iterate `AGXDeviceUserClient` children of `AGXAccelerator` in IOService plane; `IOUserClientCreator` string `pid N, name` → PID; sum `AppUsage[].accumulatedGPUTime` (ns). Rootless. macmon, mactop and the Rust sysinfo crate read it (Stats does not); mactop exposes it as experimental proportional usage. A process can own several user clients, so sum per pid.
- **Display refresh/ProMotion**: `CGDisplayMode`/`CGDisplayCopyDisplayMode` `refreshRate`, `NSScreen.maximumFramesPerSecond`; `CGDisplayStream` timing for actual cadence.
- **Sources**: https://github.com/exelban/stats/blob/master/Modules/GPU/reader.swift, https://github.com/metaspartan/mactop/blob/main/internal/app/displayfps.m, https://github.com/metaspartan/mactop/blob/main/internal/app/native_stats.go, https://github.com/oliwonders/MetalHUDHelper, https://developer.apple.com/videos/play/tech-talks/110339/

### Recurring implementation patterns

- Every sudoless tool converges on the same IOReport recipe (enumerate → filter → merge → subscribe → sample-delta); all declare the same ~15 C symbols in a bridging header. The delta is per wall-clock window; keep a persistent subscription and baseline.
- Channel-name → metric mapping is per-SoC data, not code: Stats `Platform` enum, macmon `clpc.rs` tables + `parse_acc_clusters`, mactop name filters. New chips land before code does.
- Metrics come in fallback chains: Energy Model → CLPC/PMP → SMC rails → estimate-from-bandwidth → honestly absent (VM). mactop latches fallbacks once proven dead; macmon keeps `Option`/`null` semantics.
- Everything has bogus-value filters: temps (0<t≤150, mactop ≥10 floor), fan RPM 0..100k, energy deltas ≥0 (counter resets), utilization clamped ≤100%.
- Process lists are the expensive part: Stats shells `ps`, macmon/btop enumerate processes in-process; per-process GPU needs a second IORegistry walk.
- Sampling cost ranking: sysctl/mach ticks (µs) < SMC keys (µs) < IORegistry props (ms) < IOReport merged samples (10-50ms) < PMP (100s of channels) < subprocess (10-100ms).

## Implications for Coreography

- **All metrics are achievable rootless except two**: fan *control* (needs SMJobBless helper or sudo) and context-switch/interrupt counters (kperf/DTrace, needs root - skip them). Per-app FPS: use `metalperftrace listen` on macOS 27 (1 s resolution, Metal apps), display swap counters for whole-display FPS, and a one-click Metal HUD toggle (`MetalForceHudEnabled` is user-writable, or `metalperftrace setup --enable hud --pid` for a running game on 27).
- **Architecture**: one `MetricSource` per substrate with a per-SoC platform table (copy macmon's `Sampler`+`SocInfo` split and Stats' `Platform` enum): Mach/host_statistics for CPU/RAM/load, `sysctl hw.perflevelN`+IORegistry `cluster-type`/`cpus` for topology, IOAccelerator `PerformanceStatistics` for GPU util/mem, `AGXDeviceUserClient` for per-process GPU, IOReport for residency+energy, SMC for rails/fans, IOHID for temp fallback, IOPS for battery. A single Swift bridging header (IOReport + IOHIDEventSystemClient + SMC structs) covers all of it - NeoAsitop proves the whole stack in pure Swift.
- **macOS 27 power plan**: implement the fallback ladder - Energy Model delta; if frozen (Δ=0 under load), CLPC counters via macmon's per-bundle table (open source, MIT, port `clpc.rs`+`sources.rs` approach); then SMC rails (`PP0b`+`PPbb`+`PP7b` as a rough CPU estimate, community-tested on base M3 and M5 only; `PP1b` ≈ GPU, `PZD*` DRAM, `PSTR`/`PDTR` system). Show a subtle "estimated" badge on rail-derived power.
- **Frequency/residency**: subscribe `CPU Stats`/`CPU Core Performance States` once, sample deltas at the UI interval, map residency states → `voltage-statesN-sram` tables for both per-core MHz and a DVFS histogram (socpowerbud's freq×voltage×residency view is a differentiator). Keep topology detection at init + after wake, not per tick (IORegistry walks cost ms).
- **Robustness rules to copy**: persistent subscription + baseline (macmon `get_sample_interval`), real elapsed-time power conversion (powermetrics' `elapsed_ns` lesson), never derive topology from transient `DOWN`/`OFF` residency, per-metric absence semantics (`Optional`/hidden, not 0), bogus-value clamps, IOHID client caching, minimal merged channel sets (name-filtered PMP only).
- **Fragility budget**: expect to ship per-OS/per-chip mapping updates - macOS 27 already forced three independent rewrites; M5/M6 re-letters clusters and renames channels (`MCPU`, `EACC_`, `PACC0_`, `DIE_N_`, `pmgr-child`, exclave ANE). Centralize all of it in one data-driven layer, log unmapped drivers, and add a `find-clpc`-style diagnostic mode to make future breakage triageable.
