# Enthusiast and gaming monitoring tools: Afterburner, RTSS, HWiNFO, frametime analysis (research notes)

> Coreography research notes. Sources accessed 2026-10-17.

## Summary

- The Windows enthusiast stack splits into three layers: sensor readers (HWiNFO64, HWMonitor, LibreHardwareMonitor, AIDA64), render/injection overlays (RTSS, PresentMon capture app, FrameView), and post-capture analyzers (CapFrameX, PresentMon stats CSVs). MSI Afterburner plus RTSS is the de-facto bundle that wires the first two together.
- MSI Afterburner 4.6.6 went final in October 2025 after years in beta (bundles RTSS 7.3.7), and the 4.6.7 beta line continued through October 2026 (Beta 5, build 19412). Its "Monitoring" tab established the checklist-plus-per-graph-properties pattern: enable a sensor, then independently set OSD visibility, tray icon, embedded graph, alarm colors and axis limits.
- HWiNFO64 (v8.54, Sep 30 2026) has the widest sensor coverage and the Sensor Status table (Sensor | Current | Minimum | Maximum | Average) that everything else imitates. Its free tier limits Shared Memory publishing to 12 hours, which silently breaks downstream tools (RTSS overlays, Rainmeter, Stream Deck, MoBro) unless users buy Pro (~US$29/yr Personal).
- RTSS's OverlayEditor is the most sophisticated OSD composer: layer-based hypertext with embedded graphs, dynamic colors driven by value ranges, conditional layers (e.g. "GPU Limited" badge from GPUBusy/frametime ratio), and pluggable data sources including HWiNFO, AIDA64 and PresentMon.
- Frametime analysis matured into a discipline: CapFrameX (1.9.1 stable, Sep 2026) is the reference post-capture analyzer with L-shape percentile curves, stutter/variance pies, range-slider cropping and bottleneck classification; Intel PresentMon (v2.6.0, Sep 2026) supplies the underlying metrics (CPU Busy, GPU Busy, Display Latency, Click-to-Photon, Animation Error) plus an overlay with multi-line graphs and histograms.
- The frame-generation era broke plain "FPS": PresentMon now splits FPS-Presents / FPS-Display / FPS-App, and FrameView 2.0 (Sep 2026) counts dropped and zero-display presents and reports the active frame-gen multiplier.
- Consumer-facing tools (NZXT CAM 4.76.6, Corsair iCUE 5.52.x) show the low end: a "value + sparkline" card grid and a compact always-on mini mode. CAM removed its in-game overlay, overclocking and game tracking in April 2023 to focus on monitoring and device control.
- Recurring UX pattern: session statistics (Min/Max/Average since a reset) are first-class columns; named benchmark recordings produce stats summaries (avg/min/max/1% low/0.1% low); per-sensor alarms tint OSD text or fire actions.

## Tools

### MSI Afterburner

- **Status**: Windows freeware; developed by Alexey "Unwinder" Nicolaychuk (Guru3D) for MSI, first released October 2009. Stable: 4.6.6 final, October 2025 (first stable release in over two years, bundles RTSS 7.3.7; MSI's download page also lists a Feb 2026 repackage date). Preview: 4.6.7 betas through 2026; Beta 5 build 19412 appeared on the Guru3D mirror 2026-10-08; Beta 3 (June 2026) added Voltage/Frequency Curve Editor navigation aids, thermal curve analysis and curve import/export. Works with NVIDIA, AMD and Intel GPUs including iGPUs; 4.6.6 added native RTX 50-series support, unofficial RDNA 4 support, quad-fan control, new Win 11 Dark/Light skins with a "Hide GPU" button for iGPUs, and dropped Windows XP. Development paused in 2022-2023 when sanctions prevented MSI paying the Russia-based author; resumed after. Official downloads only from msi.com and guru3d.com; MSI warns about phishing clones.
- **What it shows**: GPU core/memory/shader clocks, usage, temperature, power, voltages, fan speed (RPM and %), per-fan channels, frame rate limiter state; CPU usage per thread, clocks, temp, power; RAM and pagefile usage; and the framerate family: Framerate, Frametime, Framerate Avg/Min/Max, Framerate 1% Low / 0.1% Low (populated only while benchmark recording is active). Overclocking sliders for core/memory offset, power limit, temp limit, fan curve and a Voltage/Frequency curve editor.
- **How it shows it**: Skinned skeuomorphic main window: a central dial-style GPU readout flanked by slider banks, profile slots (1-5) and apply/reset buttons. The hardware monitor is a detachable scrollable strip of stacked line graphs, one row per enabled sensor. Configuration lives in Settings > Monitoring: an "Active hardware monitoring graphs" checklist where each row has a checkbox plus a Properties column showing flags like "in OSD". Selecting a row exposes per-graph properties: "Show in On-Screen Display" (displayed as text, graph, or both; "Graph placement" can put a mini-graph above, below or embedded inside the text column for per-core usage), "Show in tray icon" (text or barchart indicator mode), "Override graph name"/"Override group name" (Ctrl+click applies to a whole group), embedded graph width, graph color/limits, and alarm thresholds that recolor OSD output. Context menu has "Select by group"/"Select by type" for batch edits (e.g. all CPU1-CPU8 usage rows at once). The Benchmark tab defines global Begin/End recording hotkeys (commonly F9/Shift+F9); results append to a text file with total time, rendered frames and min/avg/max framerates. OSD toggle is a global hotkey (default Scroll Lock) that only works while the Settings window is closed. OSD rendering itself is delegated to the bundled RTSS.
- **Ideas worth taking**: The enable-then-configure two step (checkmark enables a metric, then independent toggles decide where it surfaces: OSD, tray, log) scales well to hundreds of sensors. "Select by group/type" batch operations keep long lists manageable. Embedded in-row mini graphs for per-core data is a smart density trick. Per-metric alarm thresholds mapped to display colors is a compact, general mechanism. Detachable monitoring panel = the "strip of stacked strip-charts" pattern Coreography wants.
- **Weaknesses / avoid**: Discoverability is poor: the checkmark must precede the "Show in On-Screen Display" checkbox (greyed out otherwise), hotkeys silently do nothing while Settings is open, and Avg/1% Low readouts stay frozen until a benchmark recording is armed. The skeuomorphic skinned UI, tiny controls and group-edit keyboard modifiers (<Ctrl>, Ctrl+M) are pure expert-folk-UI. No shared cursor, zoom or aligned cross-section across graphs.

### RivaTuner Statistics Server (RTSS)

- **Status**: Free Windows tool by the same author (Unwinder), distributed standalone via Guru3D and bundled inside MSI Afterburner. RTSS 7.3.7 final shipped with Afterburner 4.6.6 (Guru3D build dated Sep 30, 2025); it dropped the PresentMon V1 service API in favor of PresentMon V2 and added a LibreHardwareMonitor data provider plus experimental AMD Ryzen 9000 / Intel Arrow Lake support. The 7.3.5 beta cycle back in 2023 added a PresentMon data source, the "GPU busy" metric and conditional layers (Guru3D's "RTSS 7.3.5 beta 5" post is dated Sep 13, 2023). Plugin architecture introduced in 7.3.0, which also introduced the OverlayEditor plugin. A 7.3.8 beta cycle began in August 2026 (Beta 1 builds on the Guru3D mirror).
- **What it shows**: Injected in-game OSD: any metric pushed by client apps (Afterburner sensors, HWiNFO, AIDA64, Windows performance counters, its own internal HAL sources) plus native frame stats: instantaneous framerate, real-time frametime history graph, and benchmark statistics (min/avg/max/1% low/0.1% low framerate plus recording time, exposed through text formatting tags). PresentMon-sourced items include frametime, GPU activity/GPU busy, display mode (iFlip vs composed flip) and estimated input latency; RTSS can also inject NVIDIA Reflex latency markers (ReflexSetLatencyMarker).
- **How it shows it**: Classic mode renders hypertext (markup with tags like %FRAMERATE%, inline color and alignment codes) in a screen corner, plus the signature frametime graph: a horizontally scrolling ms line-chart with the refresh-rate gridline. The OverlayEditor plugin is a visual composer: overlays are layered stacks of text, bar indicators, embedded line/graph primitives and images bound to named data sources; layers have position, size, refresh period and custom units/formulas. Dynamic colors map up to five value ranges to fixed colors or blended gradients, recalculated per displayed graph point. Conditional layers show/hide by expression (the shipped demo computes GPUBusy/frametime and displays "GPU Limited" at >= 0.75). Built-in layouts include Classic, Benchmark (autoscaling frametime graph plus a dynamic distribution of the slowest frames with a highlighted 1% zone) and presentmon_frame_scale. Rendering is single-pass batched geometry (text pass then graph pass). Per-exe application profiles control detection level, stealth mode, corner position and the framerate limiter: async / front edge sync / back edge sync modes, plus Scanline Sync which steers the tearline to a chosen scanline for tear-free vsync-off; combining an exact-refresh cap with front/back edge sync is the "hybrid scanline sync" recipe. DesktopOverlayHost in the SDK renders overlays on the desktop itself.
- **Ideas worth taking**: Layers + data sources + display formatting = a small compositional model that powers users can grow into. Conditional layers are a tiny rule engine that turns thresholds into UI state. Auto-hiding its own benchmark stats when the client app displays equivalent metrics avoids double-rendered clutter. Per-application profiles with sensible global defaults.
- **Weaknesses / avoid**: Hypertext markup, INI-toggled features (SyncHotkeys=1) and forum-post changelogs make the real feature set expert-only. The limiter modes (async/front edge/back edge) are genuinely subtle; the author himself says misuse produces bad results. Windows-only, D3D injection means anti-cheat conflicts.
- **Sources**: https://forums.guru3d.com/threads/rtss-overlay-editor-megathread.436443/, https://forums.evga.com/MSI-Afterburner-RTSS-732-Final-released-m3495954.aspx, https://www.guru3d.com/story/download-rtss-7-3-5-beta-3/, https://forums.blurbusters.com/viewtopic.php?t=4916, https://www.overclock.net/threads/g3d-msi-afterburner-4-5-0.1689473/, https://montysplace.org/2025/04/19/riva-tuner-documentation-and-notes/, https://videocardz.com/newz/msi-afterburner-4-6-6-released-first-stable-update-in-over-two-years

### HWiNFO64

- **Status**: Windows sensor tool by REALiX (Martin Malik). Free for personal/non-commercial use; HWiNFO64 Pro (Personal subscription from US$29/yr since the July 2023 price rise; Lifetime perpetual option also offered; Engineer/Corporate for commercial use) adds CLI automation, unlimited Shared Memory and higher remote monitoring limits. Latest v8.54 (Sep 30, 2026); v8.55 build 6095 in beta; very fast cadence (v8.48 May 26, v8.50 Jul 8, v8.52 Aug 25 2026). Free tier limits: Shared Memory Interface deactivates after 12 hours runtime (since v7.00, March 2021), OSD limited to 5 items, remote monitoring to 5 machines/12h. ARM64, 32-bit and DOS variants exist.
- **What it shows**: The broadest sensor inventory on Windows: CPU per-core temps/clocks/power, GPU edge/hotspot/memory temps (per-chip VRAM temperature monitoring for GDDR6X/GDDR7 on NVIDIA and per-chip maps for AMD Navi in v8.52), VRM temps, voltages, fan RPM, memory timings, drive SMART/NVMe details, network rates, battery, EC-sourced board sensors. Session statistics per sensor (min/max/average). A static System Summary: three-pane CPU / motherboard+RAM / GPU overview with storage, boot (UEFI, Secure Boot, TPM) and OS build info.
- **How it shows it**: Welcome screen picks Sensors-only, Summary-only or full mode (Sensors-only skips parts of the hardware scan; returning to full mode requires restart+rescan). Sensor Status is a dense flat table grouped by device header with columns Sensor | Current | Minimum | Maximum | Average, a clock button to reset stats, and a configurable global polling period (commonly set 500-2000 ms). Right-click a row: hide, rename, custom font/color, Show Graph, add to tray, add to OSD/gadget, configure alert. Double-click opens a small dedicated live graph window per sensor (editable Y-axis; double-click toggles the parameter side-panel). Alerts tab: threshold crossing triggers popup, sound, program launch, SMTP email or Event Log entry. Tray icons per sensor with digit truncation and per-icon font/text/background colors. Logging writes selected sensors to CSV/JSON at the polling interval (v8.54 added the option to insert notes into the JSON log). OSD: built-in OSD option plus RTSS passthrough (v8.54 added multiple values on one OSD line and reporting the monitored process name in the RTSS sensor title). Shared Memory Interface publishes the whole sensor table to third parties: RTSS OverlayEditor data source, Rainmeter skins, Stream Deck plugins, MoBro dashboards. The "Gadget" provides a small desktop widget/registry fallback for integrations.
- **Ideas worth taking**: The four-column session-stats table is the most copied pattern in the category; the reset-clock affordance makes it a profiling tool. Per-sensor context menu consolidating every surfacing destination (graph, tray, OSD, alert) is good information architecture. Publishable shared-memory API turned a sensor reader into a platform. Sensors-only startup mode respects the common use case.
- **Weaknesses / avoid**: Legendary wall-of-data first impression; configuration depth requires per-sensor tabs and modal settings dialogs. Per-sensor floating graph windows do not compose into a dashboard. The 12-hour Shared Memory cutoff makes downstream integrations silently stop, a support burden documented by Stream Deck and MoBro plugin FAQs. Sensors-only and full modes are mutually exclusive at runtime.
- **Sources**: https://www.hwinfo.com/version-history/, https://www.hwinfo.com/forum/threads/hwinfo-v8-54-released.11343/, https://www.hwinfo.com/forum/threads/hwinfo-v8-52-released.11310/, https://www.hwinfo.com/licenses/, https://www.hwinfo.com/forum/threads/important-changes-to-hwinfo64-coming-soon.7092/, https://hwinfo.su/en/manual/, https://en.hwlibre.com/How-to-use-HWInfo-to-monitor-and-audit-your-system/, https://docs.slawrensen.com/hwinfo-streamdeck/faq.html, https://www.mod-bros.com/en/faq/mobro/desktop-app/hardware-monitor/data-sources, https://github.com/mcavallo-git/Coding/blob/main/windows/HWiNFO64/HWiNFO64%20-%20Good%20Settings.md, https://www.hwinfo.com/forum/threads/accessing-system-summery-info-from-sensor-mode-autorun.7984/

### CapFrameX

- **Status**: Free Windows frametime capture/analysis tool by the CXWorld team (originally DevTechProfile). Stable 1.9.1.5 (Sep 27, 2026); beta 1.9.2.1 (Oct 7, 2026). Built on Intel PresentMon: the 1.9.2 beta line bundles a maintained fork CX-PresentMon 2.6.1 (based on Intel 2.6.0, a CapFrameX build rather than an official Intel 2.6.1) fixing stale application-timing leaks and capture stalls around frame generation, plus BENCHLAB Service 2.4.0 for hardware telemetry. Runs on .NET 10. Overlay historically via RTSS; 1.9.x restored an experimental in-house overlay with digitally signed DirectX/Vulkan injection components.
- **What it shows**: Per-capture frametime series, FPS (raw and moving-average filtered), percentiles (P1, P0.2, configurable), average/min/max, adaptive standard deviation, stutter share (configurable stutter factor), frametime variance between consecutive frames, FPS threshold distributions, sensor channels (CPU/GPU/RAM/VRAM) recorded in parallel, and an automated bottleneck verdict per run: cpu-bound, gpu-bound, balanced, thermal-throttling or power-limited with confidence.
- **How it shows it**: WPF desktop app (LiveCharts) with pages for Capture, Analysis, Sensor, Overlay, Comparison and an Info dashboard. Analysis page stacks a frametime line chart, an FPS chart (raw, filtered or both) and the "L-shape" percentile curve (sorted frametimes, the classic reviewer view); extras include pie charts for stutter share and consecutive-frame variance, bar charts for FPS thresholds, selectable Y-axis scale, a range slider to crop and move a time window, an outlier-removal toggle, custom per-graph colors, legend toggle and copy-to-clipboard context menu. The Comparison view overlays multiple recordings with per-metric delta tables and mouseover highlighting in the capture list. Sensor page plots recorded hardware channels. Capture is hotkey-driven (default F11) writing .json/.csv records that double as comparison datasets. A cfx_* command-line interface exposes cfx_list_records, cfx_get_metrics, cfx_compare_records, cfx_analyze_bottleneck and friends for scripting. Dark mode, screenshot directory, remote overlay settings on other devices.
- **Ideas worth taking**: Separate capture from analysis: a small always-on recorder writes immutable session records; the analysis UI is offline and can be as dense as needed. The L-shape sorted-percentile chart and the range slider + outlier toggle pair are the honest-comparison toolkit. Sensor channels aligned on the same timeline as frametimes is exactly the "correlate metrics" experience a system monitor should offer. Derived bottleneck classification turns raw series into a verdict.
- **Weaknesses / avoid**: PresentMon-derived data has a few-second reporting lag versus RTSS's real-time graph. The overlay path has been fragile (reimplemented, re-signed). Windows-only, game-centric; no ambient always-on monitoring role. Charts are functional but generic WPF/LiveCharts in feel.
- **Sources**: https://www.capframex.com/, https://www.capframex.com/features, https://www.capframex.com/download, https://github.com/CXWorld/CapFrameX, https://github.com/CXWorld/CapFrameX/releases

### Intel PresentMon

- **Status**: Open-source Windows performance tracing and overlay stack from Intel GameTechDev. v2.6.0 (Sep 21, 2026); v2.5.1 (Jun 29, 2026; the April 2026 v2.5.0 binary was pulled over a service compatibility issue); v2.4.1 (Jan 15, 2026); v2.3.1 (Jun 10, 2025). Architecture: ETW-based PresentMon Service collects presents and GPU telemetry; a Capture Application renders a real-time overlay with a custom D3D11 renderer, configured through a CEF-based UI; console tool and SDK for other clients (CapFrameX, RTSS).
- **What it shows**: Frame metrics: FrameTime, CPU Busy, CPU Wait, GPU Busy, GPU Time, GPU Wait, GPU Latency. Frame accounting for the frame-gen era: FPS-Presents (submitted), FPS-Display (actually shown), FPS-App. Latency chain: GPU Latency, DisplayLatency (submission to scanout), MsClickToPhotonLatency, MsAllInputToPhotonLatency; plus MsAnimationError / AnimationTime (difference between previous frame's CPU delta and display delta, a smoothness signal). Presentation context: display mode (iFlip, composed flip, hybrid), dropped presents, tearing/VRR (experimental flag), PSO shader-compilation metrics (v2.6.0: count, duration, busy percentage per capture). GPU telemetry: effective frequency, power, voltage-regulator temps, memory bandwidth, fan speeds (deepest on Intel Arc; per-metric multi-device selection added in v2.6.0).
- **How it shows it**: Configurable in-game overlay: a loadout of metric readouts plus real-time chart primitives, multi-line rolling graphs and histograms of frame statistics; presets include a "Game Experience" preset emphasizing metrics correlating with perceived motion/animation quality. Per-metric device selection mixes adapters in one overlay. Unavailable metrics stay visible in pickers dimmed, with a hover reason (not on this device vs. missing in the source API) and presentmon-cli dump-caps export. Capture writes pmcap-<exe>-YYMMDD-HHMMSS.csv (per-frame rows) plus a -stats.csv with duration, frame count and average/min/90th/95th/99th FPS percentiles. Telemetry sampling is decoupled from frame rate; the service polls a device only while a client consumes it.
- **Ideas worth taking**: Splitting "FPS" into presented/displayed/app-side is the honest accounting model for frame generation and compositors. GPU Busy as a first-class metric enables the CPU-bound/GPU-bound heuristic that RTSS and CapFrameX both build on. Latency decomposed into stages (busy, wait, latency-to-scanout, click-to-photon) is the template for "why does it feel slow" UX. Dimmed-with-reason for unavailable metrics is a humane empty-state pattern.
- **Weaknesses / avoid**: Reporting lag of a few seconds vs RTSS's instantaneous graph (a PresentMon characteristic, not a bug). Overlay configuration lives in a CEF app; GPU telemetry depth is vendor-skewed to Intel; Windows-only.
- **Sources**: https://github.com/GameTechDev/PresentMon, https://github.com/GameTechDev/PresentMon/releases, https://github.com/GameTechDev/PresentMon/releases/tag/v2.3.1, https://github.com/GameTechDev/PresentMon/blob/main/README-CaptureApplication.md, https://game.intel.com/us/intel-presentmon/, https://newreleases.io/project/github/GameTechDev/PresentMon/release/v2.6.0, https://www.guru3d.com/story/download-rtss-7-3-5-beta-3/

### NVIDIA FrameView

- **Status**: Free NVIDIA utility, Windows 10/11, vendor-neutral for present tracing. v2.0 (Sep 3, 2026); v1.9 (Jun 2026) introduced the redesigned overlay architecture; v1.8/1.8.1 (Mar-Apr 2026); v1.7 (Jan 2026) targeted accuracy above 800 FPS; v1.6 (early 2025).
- **What it shows**: FPS average/1% low/high percentile stats, frametimes, PC latency (PCL) on Reflex systems, GPU clocks/temp/power including laptop power split, the active frame-generation multiplier (DLSS FG, and Smooth Motion as of 2.0), display flip-mode tag ("I" overlay tag for iFlip), per-application benchmark CSV logs.
- **How it shows it**: A minimal text OSD (FPS, percentile stats, latency readout) plus benchmark hotkeys and a companion desktop app for logs. The current overlay (architecture introduced in v1.9) renders as an independent MPO (Multi-Plane Overlay) window instead of injecting into the game's back buffer; the legacy injection overlay remains via settings.ini (EnableOverlay=True, EnableFVOverlay=False). v2.0 also changed FPS accounting to count dropped and zero-display presents so stutter and 1% lows are characterized more honestly (average FPS may read slightly higher as a side effect). Known MPO conflicts: no NIS/DSR, some exclusive-fullscreen GL/Vulkan titles, Battlefield 6 anti-cheat; mode tags F/W do not work on the new overlay.
- **Ideas worth taking**: MPO/independent-window overlay is the modern low-intrusion path (contrast: RTSS injection vs PresentMon renderer). Explicit handling of dropped and generated frames in FPS math. Overlay as pure readout: all analysis pushed to exported CSVs and the desktop app.
- **Weaknesses / avoid**: Minimal UI, no in-app analysis beyond exported logs; the new overlay's hardware flip requirements create a compatibility matrix users must debug via the "I" tag.
- **Sources**: https://www.nvidia.com/en-us/geforce/technologies/frameview/, https://www.nvidia.com/en-us/geforce/technologies/frameview/release-notes/, https://www.tomshardware.com/pc-components/gpus/nvidia-updates-frameview-performance-measurement-tool-version-1-7-promises-accurate-results-even-at-800-fps, https://www.computerbase.de/downloads/systemtools/grafikkarten/nvidia-frameview/

### OCAT

- **Status**: AMD GPUOpen's Open Capture and Analytics Tool, open source (MIT), Windows. Last release v1.6.3 (Sep 27, 2023; FSR3 compatibility, VS2022 toolset). Effectively unmaintained: open issues ask "is this project dead?". Superseded in practice by PresentMon-based tooling, though it pioneered several conventions.
- **What it shows**: FPS overlay and present capture for D3D11/12 and Vulkan using the PresentMon library; performance summary logs; an analysis backend rendering per-frame charts offline after capture; estimated driver lag metric.
- **How it shows it**: Small desktop launcher, per-app profiles, hotkey capture with optional overlay disable during recording to reduce overhead. Notable visual ideas: a lag-indicator overlay that changes color on a hotkey press (marking felt input lag during a capture, with an audible beep toggle) and an FCAT-style per-frame colored bar strip, each vertical bar colored by frametime band, the densest possible frametime fingerprint.
- **Ideas worth taking**: The FCAT color-strip: encode each frame's time as a colored sliver, turning a whole capture into a barcode where stutter regions are immediately visible. User-marked latency events during captures (subjective flag next to objective data). Capture-time option to drop the overlay for measurement purity.
- **Weaknesses / avoid**: Dead codebase, overlay compatibility rots as games update; analysis requires leaving the game anyway.
- **Sources**: https://github.com/GPUOpen-Tools/OCAT/, https://github.com/GPUOpen-Tools/OCAT/releases, https://github.com/GPUOpen-Tools/ocat/issues, https://gpuopen.com/ocat/, https://alternativeto.net/software/ocat-open-capture-and-analysis-tool/about/

### HWMonitor (CPUID)

- **Status**: Windows freemium from CPUID; v1.68 (Sep 14, 2026), frequent releases (1.56 Feb 2025 through 1.68 Sep 2026). Free version is full monitoring but feature-limited vs HWMonitor Pro (Standard ~EUR 20 with one year of updates and up to 10 remote connections; Extended ~EUR 35 for two years and 20 connections) which adds remote monitoring, tray-icon sensors, editable labels and a graph generator. ~4 MB installer, portable ZIP offered.
- **What it shows**: Motherboard/CPU temps, voltages, clocks, utilization; GPU temps/clocks/power (NVIDIA/AMD); storage temps and newer metrics (IOPS, average latency, NVMe link speed); recent additions include AMD Strix/Kraken NPU power, clocks, TOPS and memory bandwidth, PCIe error counters.
- **How it shows it**: A single scrolling tree: device nodes expand to sensor groups (temperatures, voltages, fans, utilization, powers, clocks) with Value | Min | Max columns, values bold on update. Min/max persist for the session. Dark mode option; remembers expanded node state between runs. No graphs in the free tier, no customization beyond hiding; deliberately zero-configuration.
- **Ideas worth taking**: The zero-setup promise: launch and everything visible is already correct. Min/Max next to the live value is the cheapest possible session statistics. Remembers UI expansion state, small kindness.
- **Weaknesses / avoid**: Dead-end UI: no logging, no alerts, no graphing without Pro, no per-sensor presentation control. Fine as a checker, not a monitor.
- **Sources**: https://www.cpuid.com/softwares/HWmonitor.html, https://www.majorgeeks.com/files/details/hwmonitor.html, https://download.cpuid.com/hwmonitor/hwm_readme.pdf

### AIDA64

- **Status**: Commercial Windows diagnostics suite from FinalWire (paid with trial; Extreme, Engineer, Business, Network Audit editions). Extreme v8.40.5000 stable (Sep 15, 2026); betas at 8.40.85xx through Oct 15, 2026. The 8.x scheme began with v8.00 (Sep 15, 2025), which moved to native 64-bit binaries and dropped 32-bit Windows and XP x64. v8.30 (April 28, 2026) added "AIDA FPS", an Extreme-only in-game FPS capture module for DX11/12.
- **What it shows**: Extremely detailed hardware/software inventory (50+ pages each per marketing), 250+ sensor device readings (temps, voltages, fans, power), CPU/GPU/memory/disk benchmarks, a system stability test, and monitoring surfaces: SensorPanel, LCD/VFD external displays (50+ models: Matrix Orbital, Turzx/Turing, Thermalright, Waveshare), OSD panel, desktop gadget, Logitech/Razer LCDs, smartphone remote monitoring, taskbar tray icons.
- **How it shows it**: Classic tree-of-pages main window (categories on the left, detail page right). The SensorPanel is the distinctive piece: a freeform canvas where users place graphs, analog-style gauges, bars, custom bitmaps and static/dynamic text bound to any sensor reading, arranged arbitrarily and skinned via community .sensorpanel packs (compressed SPZIP format introduced in v7.50, Dec 2024, and headlined again in v8.00). Sensor logging to CSV/HTML, configurable alerts, and a separate stability-test window charting temperature and CPU throttling during load. Recent releases put real work into multi-monitor and per-monitor DPI behavior of windows and panels. The new AIDA FPS module brings frametime-era measurement (real-time FPS capture) into a previously sensor-only product.
- **Ideas worth taking**: Freeform canvas dashboards are the maximal-personalization endgame: users invest hours making SensorPanels match their rig. Gauge/bar/graph/text as a palette of sensor-bound widgets is a reusable primitive set. External-display targets (LCD, phone) treat monitoring as an ambient output, not a window.
- **Weaknesses / avoid**: Dated Win32 chrome; SensorPanel editing is fiddly bitmap-era work; price; feature sprawl (audit, benchmarks, network admin) dwarfs the monitoring core.

### LibreHardwareMonitor

### Special K

- **Status**: Freeware game-mod framework by Kaldaien (Andon M. Coleman), Windows, distributed via its own installer and wiki; public GitHub repo lags development. The third major frame-pacing tool alongside RTSS and in-game limiters, and the one modders reach for when a game ships without a working cap.
- **What it shows**: Per-game injection frontend (local DLL or global service) with an in-game control panel: live framerate and frametime graphs, per-frame statistics, present/monotonic counters, texture and shader tooling, HDR retrofit controls, NVIDIA Reflex toggles, and input/display diagnostics.

## Key performance concepts

- **Frametime vs FPS**: FPS is a rate over an interval; frametime is the per-frame duration (ms) between presents. Two runs averaging 60 FPS can differ completely in feel: a flat 16.7 ms line vs alternating 5 ms/28 ms frames. Frametime exposes spikes FPS hides, which is why the RTSS frametime graph became standard OSD furniture. CapFrameX documents the subtler trap: instantaneous in-game FPS (inverse of the last frametime) will not match analysis-window averages, so the same run "reads" differently in different tools.
- **1% low / 0.1% low**: the mean of the worst 1% or 0.1% of frametimes (converted back to FPS). It quantifies the stutter tail an average hides; RTSS computes min/avg/max/1%/0.1% live in the OSD, and PresentMon's stats CSV emits 90th/95th/99th percentiles. Reviewers (TechReport's early frame-time work, then everyone) made it the standard second metric after average FPS.
- **Frame pacing**: the regularity of present intervals. VRR displays, in-game limiters and RTSS's async/front-edge/back-edge limiter modes exist to keep the frametime line flat; Scanline Sync goes further, steering the tearline to a fixed scanline for near-vsync-off latency with vsync-on smoothness.
- **Stutter**: a frametime outlier or pacing irregularity the eye catches. Tooling decomposes it: CapFrameX's stutter factor and consecutive-frame variance pies; PresentMon's MsAnimationError (previous frame's CPU delta vs display delta) which isolates hitching even when average FPS looks fine; PSO compilation metrics that blame shader compiles.
- **CPU-bound vs GPU-bound**: approximated by comparing how long each side works per frame. PresentMon exposes CPU Busy and GPU Busy; the shipped RTSS conditional-layer demo flags "GPU Limited" when GPUBusy/frametime >= 0.75 (closer to 1 = GPU saturated); CapFrameX classifies whole captures into cpu-bound/gpu-bound/balanced/throttling with a confidence score.
- **Latency chain**: input-to-photon decomposed: input sampling, simulation (CPU Busy), render queue wait, GPU work (GPU Busy/Time), compositing, scanout (DisplayLatency); PresentMon reports MsClickToPhotonLatency and MsAllInputToPhotonLatency. Flip model matters measurably: the RTSS PresentMon demo shows composed flip adding roughly one frame (~16 ms at 60 Hz) the moment a recording overlay activates.
- **Frame generation accounting**: generated frames inflate presented counts without display-side improvement, so PresentMon splits FPS-Presents / FPS-Display / FPS-App, and FrameView 2.0 counts dropped and zero-display presents and prints the active multiplier (DLSS FG, Smooth Motion).

## Cross-cutting patterns

- **Session-stats table**: Current | Min | Max | Average columns with a reset control (HWiNFO, HWMonitor, LibreHardwareMonitor). Universally understood; turns "watch a number" into "profile a session".
- **Checklist then inspector**: pick metrics from a long catalog, then set per-metric surfacing (Afterburner's Monitoring tab, iCUE's sensor picker). Scales to hundreds of sensors while keeping the default view small.
- **Value + sparkline tile**: the card grid as ambient dashboard (CAM, iCUE home sensors); graph-per-row strips for dense views (Afterburner monitor, HWiNFO graphs); embedded in-row mini graphs for per-core scale (Afterburner).
- **Tray/menu-bar icons as the minimal surface**: per-sensor icon with custom color, truncation, text or bar mode (HWiNFO, Afterburner, FanControl, iCUE battery).
- **Alarms as color, not just dialogs**: threshold crossing recolors OSD text (Afterburner/RTSS dynamic colors, up to 5 ranges incl. gradients) or fires actions (HWiNFO: popup, beep, program, SMTP, event log).
- **Named capture sessions**: hotkey-bounded recordings producing stats summaries (Afterburner benchmark tab, PresentMon pmcap CSVs, CapFrameX records, FrameView logs). Analysis happens on records, not on the live view.
- **Monitors as platforms**: shared memory (HWiNFO SHM), libraries (LibreHardwareMonitorLib), services (PresentMon Service) and widget APIs (iCUE) let third parties build on the sensor layer; licensing limits on those interfaces (HWiNFO's 12-hour SHM) propagate as user-facing failures downstream.
- **Overlay render paths trade intrusion for compatibility**: DLL-injected hypertext (RTSS), dedicated D3D11 overlay renderer (PresentMon), independent MPO window (FrameView 2.0). Each solves the "draw over a fullscreen app" problem differently with different anti-cheat/latency profiles.
- **Percentile-first statistics**: 1%/0.1% lows and sorted-percentile (L-shape) curves are the expected tail metrics in gaming tools; averages alone are treated as marketing.
- **Density vs approachability fork**: expert tools (HWiNFO, Afterburner, RTSS) choose dense tables and forum-documented options; consumer tools (CAM, iCUE) choose sparse cards and few choices. Nothing in the space serves both well.

## Implications for Coreography

- **Adopt the session-stats table as the primary dense view**: rows of metrics with Current/Min/Max/Average plus a sparkline cell and a reset-stats control. This is the proven power-user pattern and maps directly onto a SwiftUI table with custom cells.
- **Checklist-then-inspector for metric selection**: a searchable sensor catalog; enabling a metric reveals an inspector with surface toggles (main chart, menu bar, pinned mini window, log) plus color, format, axis and alert-threshold settings. Same model as Afterburner/HWiNFO, minus their two-step trap: one checkbox should mean "track", not "track but render nowhere".
- **Menu bar = tray icons done natively**: per-metric menu bar items in text or mini-bar style with threshold tinting; the established minimal surface.
- **Alarms as dynamic color + optional notification**: per-metric range-to-color mapping (Afterburner/RTSS model) is compact and extensible to notification actions later.
- **Borrow frametime-tool honesty for all metrics**: offer percentile views (sorted/L-shape curve, p99/p95) for captured sessions and show tail stats next to averages wherever a distribution exists (disk latency, CPU spikes, network). CapFrameX proves users understand these when presented well.
- **Named capture sessions**: a start/stop recorder writing immutable sessions with auto stats summaries (avg/min/max/p99), replayable in a stacked-timeline analysis view with a range slider and outlier toggle; aligns naturally with "what just happened on my Mac" workflows.
- **Derived verdict metrics**: compute boundedness-style indicators (e.g. GPU-busy/frametime analogs: CPU pressure vs utilization, memory pressure vs swap activity) and surface them as badges; PresentMon/RTSS show a simple ratio-plus-threshold reads instantly.
- **Compact/mini mode is a first-class citizen**: CAM's mini mode and Afterburner's detach precedent; a small always-on-top strip of cards serves the ambient-monitoring role Activity Monitor cannot.
- **Avoid the catalogue of sins**: skeuomorphic skins and tiny click targets; hotkeys dead while settings are open; per-sensor floating graph windows instead of a composed dashboard; configuration depth requiring forum archaeology; silent integration limits. Also avoid CAM-style oversimplification that abandons depth entirely.
- **Design language guidance**: default to Mac-native conventions (SF monospaced digits for live values, system semantic colors, vibrancy); reserve dense small-type layouts for an explicit expert/table mode. Threshold tinting should prefer accessibility-aware color pairs, not the raw red/green of gaming tools.
- **Data sources as an interface**: the HWiNFO-SHM lesson is that a clean, documented metrics API (plus CSV/JSON logging) buys an ecosystem and headless use; design the metric catalog as queryable from day one.
